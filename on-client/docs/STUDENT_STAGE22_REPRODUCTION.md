## 5. 데이터 보존·백업·복원 계획과 한계

- 코드·문서: 원래 Git 저장소와 기존 커밋을 보존합니다. 복원 시 필요한 커밋을 새 폴더에 clone/checkout하고 git rev-parse HEAD로 대조합니다. 이번 복제는 커밋된 원문만 대상으로 하므로 미커밋·Git 제외 파일은 복구하지 않습니다.
- 인증·개인 설정: 비밀값을 Git·문서·원문 JSON에 포함하지 않습니다. 새 환경에서는 담당자가 승인한 방법으로 준비합니다. 인증 파일의 무조건 복사는 복원 절차가 아닙니다.
- 업무·계정 자료: 접속 기록·기기·세션·XDR 자료의 원본은 연동 시스템에 있습니다. Git clone으로 이 자료가 백업·복구되지는 않습니다. 원천 운영자의 보존 정책·승인된 백업 시점·복원 절차를 확인해야 합니다.
- 조치 저장소: src/actions/store.mjs의 존재는 확인되지만 실제 데이터 경로·저장 형식별 백업·복원 시험은 미확인입니다. 운영자가 저장 방식과 일관성 있는 백업 방법을 확인한 뒤 백업 시점·보관 위치·책임자를 기록해야 합니다. 실행 중 저장소를 임의 복사하지 않습니다.
- 복원 시험: 원래 데이터와 분리된 위치에서 승인된 백업을 복원하고 기록 건수·대상 범위·요청/접수 식별자를 원본과 대조하는 계획입니다. 실제 복원은 수행하지 않았으며 데이터 복구 가능성을 보장하지 않습니다.

## 6. 최종 제출 커밋과 검증 범위


문서만 달라야 기본 실행 증거를 코드 변경 없이 연결할 수 있습니다. 코드·실행 설정·의존성이 바뀌면 새 최종 커밋을 별도 폴더에 받아 다시 재현해야 합니다. 최종 제출 커밋 자체에서의 실행은 아직 수행하지 않았고, 문서 변경만 있는지 최종 Git 대조도 커밋 후 남아 있습니다. 이 한계를 숨기거나 최종 버전 전체 성공으로 표현하지 않습니다.
